## 1. Зачем программисту история изменений

Представим, что программа правильно вычисляет стоимость покупки. Мы добавляем доставку, но после изменения получаем неверный результат. Нужно узнать, что изменилось, сравнить варианты и при необходимости вернуться к предыдущему решению.

Без специальных инструментов появляются папки:

```text
purchase/
purchase_copy/
purchase_final/
purchase_final_2/
purchase_really_final/
```

Такие копии трудно сравнивать. Из названия неясно, какие изменения сделаны, почему они потребовались и какой вариант нужно продолжать. Если два студента независимо редактируют проект, появляется ещё один вопрос: как объединить их работу?

**Система контроля версий**, или **VCS** (*Version Control System*), помогает сохранять версии файлов и отслеживать историю проекта. Она позволяет выяснить:

- какие файлы изменились;
- какие строки были добавлены и удалены;
- кто указан автором изменения;
- когда версия была сохранена и каким сообщением сопровождалась;
- как получить прежнее состояние или отменить отдельное изменение.

Контроль версий полезен и при индивидуальной работе. Студент может вернуться к решению, которое работало вчера, преподаватель - проследить развитие задания, а команда - обсудить конкретное изменение.

### 1.1. Сохранение файла и сохранение версии

Когда мы нажимаем **Сохранить** в редакторе, изменяется файл на диске. Git не создаёт коммит при каждом таком нажатии. Разработчик самостоятельно выбирает момент, когда очередное законченное изменение следует добавить в историю.

Для программы покупки история может выглядеть так:

```text
Версия 1: добавлен расчёт цены и количества
Версия 2: добавлена стоимость доставки
Версия 3: исправлено повторное прибавление доставки
```

Хорошая история рассказывает, как развивалось решение. Сообщения «что-то изменил» или «готово» почти не помогают понять проект через неделю.

### 1.2. Что Git не делает автоматически

Git сохраняет выбранные состояния, но не определяет, правильно ли программа решает задачу. В историю можно записать как рабочую программу, так и программу с ошибкой. Поэтому перед фиксацией изменения нужно прочитать различия и проверить результат.

Локальная история хранится на том же устройстве, что и проект. Если устройство выйдет из строя, можно потерять и файлы, и историю. Для восстановления после такой потери нужны резервные копии или копии репозитория на других устройствах.

**Проверьте понимание:** файл сохранён в редакторе, но коммит не создан. Новая версия есть в рабочей папке, однако она ещё не зафиксирована в истории Git.

## 2. Основные понятия

**Репозиторий** (*repository*) - хранилище истории проекта и служебных данных системы контроля версий. В обычном локальном Git-проекте служебные данные находятся в скрытой папке `.git`.

**Рабочая папка**, или **рабочее дерево** (*working tree*), - файлы, с которыми разработчик работает сейчас: открывает в редакторе, изменяет и запускает. В исходной лекции используется также выражение «рабочая копия» (*working copy*).

**Коммит** (*commit*) - зафиксированное состояние проекта с сопутствующими данными. У него есть идентификатор, сведения об авторе, сообщение и, как правило, ссылка на предыдущее состояние. У первого коммита родителя нет, а у коммита слияния родителей может быть несколько.

**История** - связанные между собой коммиты. Идентификатор позволяет обратиться к конкретному коммиту, даже если несколько сообщений похожи.

**Удалённый репозиторий** (*remote repository*) - другой репозиторий, с которым настроен обмен. Например, он может находиться на GitHub. Для Git слово «удалённый» описывает роль в обмене; технически такой репозиторий может располагаться и по другому локальному пути.

**Ветка** (*branch*) - именованная линия разработки. В Git имя ветки указывает на коммит и перемещается при добавлении новых коммитов в этой ветке. Основную ветку в примерах назовём `main`.

| Понятие | Пример в учебном проекте |
|---|---|
| Рабочая папка | Каталог `purchase-demo` с файлом `purchase.py` |
| Локальный репозиторий | История и служебные данные внутри `purchase-demo/.git` |
| Коммит | Состояние с сообщением «Добавлен расчёт стоимости покупки» |
| Ветка | `main` или `delivery` |
| Удалённый репозиторий | Репозиторий проекта на GitHub |

Не редактируйте содержимое `.git` вручную в рамках этой работы: для управления историей используются команды Git или графический клиент.

## 3. Централизованные и распределённые системы

### 3.1. Централизованная модель

В **централизованной системе контроля версий** основная история находится на сервере. Разработчики получают рабочие копии, редактируют файлы и передают изменения в центральный репозиторий.

![Централизованная модель: общий репозиторий на сервере и рабочие копии разработчиков](images/lecture_2/p02_01.png)

*Рисунок 1. Централизованная система контроля версий. Из исходного PDF, с. 2.*

Слова на схеме: **Server** - сервер; **Central repository** - центральный репозиторий; **Working copy** - рабочая копия; **Workstation** - рабочая станция разработчика.

Примеры таких систем - **CVS** (*Concurrent Versions System*) и **Subversion**, или **SVN**. Они приведены в исходной лекции как представители централизованного подхода.

Центральное хранилище удобно как единая точка управления проектом. Однако недоступность сервера ограничивает операции, которым требуется его история или запись в неё. При этом редактировать уже полученные локальные файлы обычно можно и без соединения.

### 3.2. Распределённая модель

В **распределённой системе**, или **DVCS** (*Distributed Version Control System*), разработчик работает с собственным локальным репозиторием. Он может сохранять коммиты и просматривать доступную локально историю без соединения с сервером.

![Распределённая модель: серверный репозиторий и локальные репозитории с рабочими копиями](images/lecture_2/p03_01.png)

*Рисунок 2. Распределённая система контроля версий. Из исходного PDF, с. 3.*

На схеме у каждой рабочей станции есть не только рабочая копия, но и **Repository** - репозиторий. Разработчик сначала фиксирует работу локально, а затем обменивается изменениями с другими репозиториями.

Команда может договориться считать один серверный репозиторий основным. Это организационная договорённость: распределённая модель не требует, чтобы вся работа выполнялась только через единственный сервер.

Примеры DVCS - **Git** и **Mercurial**. Командная утилита Mercurial называется `hg`; в нашем курсе будем пользоваться Git.

### 3.3. Сравнение моделей

| Вопрос | Централизованная модель | Распределённая модель на примере Git |
|---|---|---|
| Где основная история? | На центральном сервере | В локальных репозиториях; обмен объединяет доступную историю |
| Куда записывается обычный коммит? | В центральное хранилище | В локальный репозиторий |
| Нужна ли сеть для локального коммита? | Обычно требуется соединение с сервером | Нет |
| Как передать результат команде? | Зафиксировать в центральном хранилище | Отдельно отправить коммиты |
| Может ли быть общий сервер? | Это основа модели | Да, как согласованная точка обмена |

При обычном полном клонировании Git получает историю проекта. Существуют и специальные сокращённые способы клонирования, поэтому утверждение «любая копия всегда содержит абсолютно всё» было бы слишком сильным.

## 4. Git, GitHub и GitHub Desktop

Это связанные, но разные инструменты.

| Название | Назначение | Что делает студент |
|---|---|---|
| **Git** | Распределённая система контроля версий | Создаёт коммиты, сравнивает версии, работает с ветками |
| **GitHub** | Сервис размещения репозиториев и совместной разработки | Хранит доступную команде копию, обсуждает изменения |
| **GitHub Desktop** | Графическое приложение для работы с Git и GitHub | Выбирает файлы, создаёт коммиты и запускает обмен кнопками |

Git можно использовать без учётной записи GitHub и без Интернета. GitHub Desktop не является самим сайтом GitHub. Установка клиента также не означает, что любой проект на компьютере уже опубликован.

Например, студент изменил `purchase.py` и создал коммит в GitHub Desktop. Коммит находится в локальном репозитории. Чтобы он появился в связанном репозитории на GitHub, нужно выполнить отправку.

Графический интерфейс и терминал дают разные способы управления одной историей. Для понимания полезно знать, какая операция стоит за кнопкой.

## 5. Как устроена работа с Git: три области

### 5.1. Упрощённая модель из двух областей

В исходной лекции сначала показана схема «рабочая копия - репозиторий». Она помогает отделить редактируемые файлы от сохранённой истории.

![Упрощённая схема репозитория и рабочей копии со стрелками commit и checkout](images/lecture_2/p20_diagram.png)

*Рисунок 3. Модель двух областей из исходного PDF, с. 20.*

Стрелка `commit` означает фиксацию состояния. Стрелка `checkout` иллюстрирует получение выбранного состояния из истории в рабочие файлы. **В Git `checkout` сам по себе не загружает свежие изменения с сервера.** Получение данных от другого репозитория - отдельная операция.

### 5.2. Рабочая папка, индекс и коммит

Для обычного цикла работы с Git нужна третья область - **индекс**, или **область подготовки** (*staging area*, *stage*).

![Три области Git: рабочая копия, stage и репозиторий](images/lecture_2/p21_diagram.png)

*Рисунок 4. Область подготовки между рабочей копией и репозиторием. Из исходного PDF, с. 21.*

На старой схеме stage назван «кэшем». В этой лекции будем говорить **индекс** или **область подготовки**: это содержимое, из которого формируется следующий коммит.

```text
Редактор
   |
   | сохранить файл
   v
Рабочая папка
   |
   | git add
   v
Индекс: подготовленное состояние
   |
   | git commit
   v
Локальный репозиторий: новый коммит
   |
   | git push
   v
Удалённый репозиторий
```

Первые три области находятся на компьютере разработчика. Удалённый репозиторий показан отдельно для понимания обмена; он не является частью модели «трёх деревьев».

Технически под тремя деревьями обычно рассматривают рабочее дерево, индекс и дерево текущего коммита `HEAD`. Сам репозиторий содержит гораздо больше, чем одно состояние: историю, объекты и ссылки. Для первых действий достаточно различать редактирование, подготовку и фиксацию. Представление Git о снимках проекта описано в [официальной книге Pro Git](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F).

### 5.3. Зачем нужен индекс

Допустим, мы изменили программу и одновременно начали переписывать её описание. Программа уже проверена, а описание ещё не закончено. Индекс позволяет подготовить только программу и сохранить её отдельным коммитом.

Команда `git add purchase.py` подготавливает содержимое файла **на момент выполнения команды**. Если после этого снова отредактировать файл, последняя правка автоматически в индекс не попадёт. Чтобы включить её, нужно ещё раз выполнить `git add`.

| Действие | Рабочая папка | Индекс | Последний коммит |
|---|---|---|---|
| Исходное состояние | Вариант A | Вариант A | Вариант A |
| Изменили файл | Вариант B | Вариант A | Вариант A |
| Выполнили `git add` | Вариант B | Вариант B | Вариант A |
| Снова изменили файл | Вариант C | Вариант B | Вариант A |
| Выполнили обычный `git commit` | Вариант C | Вариант B | Вариант B |

В последней строке коммит содержит B, а C остаётся незакоммиченным изменением рабочей папки. Это поведение объясняет [справка `git add`](https://git-scm.com/docs/git-add).

### 5.4. Как проверить три области

```bash
git status
git diff
git diff --staged
```

- `git status` показывает общее состояние: новые, изменённые и подготовленные файлы.
- `git diff` сравнивает рабочие файлы с индексом для отслеживаемого содержимого.
- `git diff --staged` показывает различия между индексом и текущим коммитом: то, что войдёт в следующий обычный коммит.

Новый, ещё не отслеживаемый файл виден в `git status`, но его содержимое не обязано появляться в обычном `git diff`.

В Windows распространены окончания строк **CRLF**, а в Linux и macOS - **LF**. ## 7. Первоначальная настройка Git

### 7.1. Уровни настроек

| Уровень | Параметр команды | Область действия |
|---|---|---|
| Системный | `--system` | Пользователи данной установки Git |
| Пользовательский | `--global` | Репозитории текущего пользователя |
| Локальный | `--local` | Текущий репозиторий |

Для обычной настройки автора достаточно пользовательского уровня. Если для конкретного проекта требуется другое имя или адрес, задайте локальное значение внутри его папки. В этих трёх уровнях локальное значение имеет приоритет над пользовательским, а пользовательское - над системным.

### 7.2. Автор коммитов

```bash
git config --global user.name "Иван Петров"
git config --global user.email "student@example.com"
```

Замените пример своими данными. Они записываются в сведения об авторе новых коммитов. Эти команды **не выполняют вход на GitHub** и не проверяют владение адресом почты. Такая запись автора также не является криптографической подписью коммита.

Проверка:

```bash
git config --get user.name
git config --get user.email
git config --list --show-origin
```

Последняя команда показывает настройки и источники, из которых они прочитаны. Поэтому не нужно запоминать путь системного конфигурационного файла из старого скриншота: он зависит от установки. Уровни и параметры описаны в [справке `git config`](https://git-scm.com/docs/git-config).

### 7.3. При необходимости - редактор

Для Windows можно указать Блокнот:

```bash
git config --global core.editor "notepad.exe"
```

Команда задаёт редактор, который Git запускает, когда требуется ввод текста. Если привычный редактор уже выбран при установке, менять его для выполнения лекции не обязательно.

<a id="section-8"></a>

## 8. Первый локальный репозиторий

### 8.1. Создаём отдельную папку

Откройте терминал в каталоге для учебных работ. Убедитесь, что в нём ещё нет папки `purchase-demo`, затем выполните:

```bash
mkdir purchase-demo
cd purchase-demo
git init -b main
git status
```

`mkdir` создаёт папку, `cd` переводит терминал в неё. `git init -b main` создаёт локальный репозиторий с начальным именем ветки `main`. Интернет для этих действий не нужен.

Пока в истории нет коммитов. Git может вывести сообщение `No commits yet`.

### 8.2. Добавляем программу

В редакторе создайте внутри `purchase-demo` файл `purchase.py`:

```python
price = 50
quantity = 3
total = price * quantity
print(total)
```

Сохраните файл и запустите его:

```bash
python purchase.py
```

Ожидаемый результат - `150`. Если в вашей установке Python запускается командой `py`, используйте `py purchase.py`. Git хранит программу, а выполняет её интерпретатор Python.

Проверьте состояние:

```bash
git status
```

Файл появится среди **Untracked files** - ещё не отслеживаемых файлов. Его наличие в папке не означает, что он включён в историю.

### 8.3. Готовим и создаём первый коммит

```bash
git add purchase.py
git diff --staged
git commit -m "Добавлен расчёт стоимости покупки"
git status
```

Сначала мы подготовили файл, затем посмотрели, что сохраняем, и создали коммит. Параметр `-m` передаёт сообщение прямо из командной строки.

Если других изменений нет, Git сообщит `nothing to commit, working tree clean`. Это означает согласованность отслеживаемых рабочих файлов, индекса и текущего коммита. Это сообщение не говорит, что программа проверена на все ошибки или что коммиты уже отправлены на сервер.

### 8.4. Сохраняем второе изменение

Замените содержимое `purchase.py`:

```python
price = 50
quantity = 3
delivery = 100
total = price * quantity + delivery
print(total)
```

Теперь результат - `250`: товары стоят 150, доставка - ещё 100.

```bash
python purchase.py
git diff
git add purchase.py
git diff --staged
git commit -m "Добавлена стоимость доставки"
git log --oneline
```

В истории должно быть два коммита; новый выводится первым. Перед сообщением Git показывает сокращённый идентификатор. Он будет отличаться на разных компьютерах.

**Проверьте понимание:** после второго коммита оба состояния доступны в локальной истории. Ни один из них ещё не отправлен на GitHub, поскольку мы не настраивали удалённый репозиторий.

<a id="section-9"></a>

## 9. Как выбирать изменения для коммита

### 9.1. Один коммит - одна понятная задача

Создайте рядом с программой файл `README.md` с описанием:

```text
# Расчёт покупки

Программа считает стоимость товаров с доставкой.
Запуск: python purchase.py
```

Если описание готово, сохраните его отдельно:

```bash
git add README.md
git diff --staged
git commit -m "Добавлено описание запуска программы"
```

Так в истории отдельно видны изменение расчёта и добавление документации. Позднее их легче обсуждать и находить.

Перед каждым коммитом задайте себе три вопроса: что изменилось, почему это нужно и как проверен результат. Сообщение коммита должно кратко отвечать хотя бы на первый вопрос.

| Неинформативное сообщение | Более понятное сообщение |
|---|---|
| `update` | `Добавлена стоимость доставки` |
| `fix` | `Исправлено двойное прибавление доставки` |
| `готово` | `Добавлено описание запуска программы` |

### 9.2. Убираем файл из области подготовки

Если в репозитории уже есть коммит и вы подготовили файл по ошибке:

```bash
git restore --staged README.md
```

Команда возвращает запись файла в индексе к состоянию текущего коммита. Изменения рабочего файла сохраняются. Новый файл, которого не было в коммите, снова станет неотслеживаемым.

Не путайте её с `git restore README.md`: без `--staged` команда восстанавливает рабочий файл из индекса и может убрать его неподготовленные правки. Выполнять второй вариант в этом упражнении не нужно. Области восстановления описаны в [справке `git restore`](https://git-scm.com/docs/git-restore).

### 9.3. Почему сначала используем имена файлов

Вместо одного файла можно подготовить сразу несколько, например командой `git add .`. Но в учебной работе явные имена помогают замечать, что попадёт в историю. Даже при использовании `git add .` перед коммитом нужно читать `git status` и `git diff --staged`.

<a id="section-10"></a>

## 10. Какие файлы хранить в репозитории

В репозитории учебной программы обычно нужны исходный код, описание запуска и необходимые материалы. Временные результаты, локальные настройки и автоматически создаваемые файлы часто сохранять не нужно.

Файл **`.gitignore`** задаёт шаблоны для неотслеживаемых файлов, которые Git должен игнорировать. Пример для небольшого Python-проекта:

```text
__pycache__/
*.pyc
.venv/
.env
```

Здесь указаны кэш Python, файлы байт-кода, локальное виртуальное окружение и файл переменных окружения, в котором могут находиться секреты. Сам `.gitignore` обычно включают в историю:

```bash
git add .gitignore
git commit -m "Добавлены правила игнорирования локальных файлов"
```

`.gitignore` не удаляет уже сохранённые данные из истории и не перестаёт отслеживать ранее добавленный файл автоматически. Поэтому пароли и токены нельзя сначала коммитить, а потом рассчитывать скрыть с помощью игнорирования.

Изображения и PDF можно хранить в Git, но обычное построчное сравнение подходит прежде всего тексту. Изменение картинки обычно выглядит как замена двоичного файла. В лекционном проекте Markdown и связанные с ним изображения следует передавать вместе, чтобы ссылки на иллюстрации работали.

## 12. Обмен изменениями и ветви

### 12.1. Команды, которые важно различать

| Команда | Что делает |
|---|---|
| `git init` | Создаёт локальный репозиторий |
| `git clone АДРЕС` | Создаёт локальную копию существующего репозитория |
| `git add ФАЙЛ` | Подготавливает содержимое для следующего коммита |
| `git commit` | Создаёт локальный коммит |
| `git fetch` | Получает данные из удалённого репозитория без слияния с текущей веткой |
| `git pull` | Получает данные и включает изменения в текущую ветку выбранным способом |
| `git push` | Отправляет коммиты и обновляет разрешённые удалённые ссылки |

Слова `АДРЕС` и `ФАЙЛ` в таблице - обозначения подставляемых значений, а не текст для буквального ввода.

После обычного клонирования источник получает короткое имя **`origin`**. Это имя настройки, а не специальный вид сервера.

```bash
git remote -v
```

Команда показывает настроенные адреса обмена. В локальном проекте, где удалённый репозиторий ещё не добавлен, вывод может быть пустым.

### 12.2. Получение изменений

В чистой рабочей папке клонированного проекта, где текущая ветка уже связана с удалённой, можно выполнить:

```bash
git pull --ff-only
```

**Fast-forward** означает, что указатель ветки можно просто переместить вперёд по уже существующей истории. Если локальная и удалённая ветви разошлись, `--ff-only` остановит интеграцию. Нужно изучить ситуацию и выбрать способ объединения. Получение данных и способы интеграции описаны в [справке `git pull`](https://git-scm.com/docs/git-pull).

Перед получением изменений проверьте `git status` и сохраните законченную работу коммитом. Важно понимать, в какой ветке вы находитесь и с каким репозиторием обмениваетесь данными.

### 12.3. Ветки

Вернёмся к локальному `purchase-demo`. Предположим, нужно попробовать другой расчёт доставки, сохранив основную линию разработки. При чистой рабочей папке создадим ветку:

```bash
git switch -c delivery
```

Теперь новые коммиты будут добавляться в `delivery`. После редактирования, проверки и коммита можно вернуться:

```bash
git switch main
```

Git обновит рабочие файлы в соответствии с выбранной веткой. Ветки не требуют вручную создавать папки `final_2` и `final_3`.

```text
A---B---C  main
     \
      D    delivery
```

Буквы обозначают коммиты. После B разработка продолжилась двумя путями: C в основной ветке и D в ветке доставки. Это схема возможной истории, а не обязательный результат только двух команд выше.

### 12.4. Слияние и конфликты

**Слияние** (*merge*) объединяет линии разработки. Если в `delivery` уже есть проверенный коммит, то из `main` его изменения можно включить командой:

```bash
git merge delivery
```

Git способен автоматически объединять многие независимые правки. Если обе стороны по-разному изменили один фрагмент, может возникнуть **конфликт**. Тогда требуется решение человека: какое содержимое должно остаться?

Например, один участник заменил `delivery = 100` на `delivery = 150`, а другой - на `delivery = 0`. Git не знает, соответствует ли задаче платная или бесплатная доставка. Нужно свериться с требованиями, отредактировать конфликтующий файл, убрать маркеры конфликта, проверить программу, выполнить `git add` для исправленного файла и завершить слияние коммитом.

Даже автоматическое слияние без конфликта требует проверки программы: отсутствие текстового конфликта ещё не гарантирует правильное поведение.

<a id="section-13"></a>

## 13. Типичные ошибки начинающего

| Ситуация | Объяснение и следующий шаг |
|---|---|
| `git` не найден | Проверьте установку и откройте новое окно терминала |
| `not a git repository` | Терминал находится вне репозитория; перейдите в нужную папку |
| Git просит указать автора | Настройте `user.name` и `user.email` |
| Файл сохранён, но коммита нет | Выполните подготовку и фиксацию после проверки |
| Последняя правка не вошла в коммит | Возможно, файл редактировали после `git add`; сравните рабочий файл и индекс |
| Коммит не появился на GitHub | Проверьте удалённый репозиторий и отправьте коммиты |
| `git diff` пуст, хотя файл новый | Неотслеживаемые файлы смотрите через `git status` |
| Файл добавили в `.gitignore`, но он продолжает отслеживаться | Игнорирование не отменяет прежнее добавление в историю |
| `pull --ff-only` не завершился | Истории могли разойтись; изучите сообщение и ветки перед объединением |
| История есть, но результат программы неверен | Git сохраняет версии; корректность проверяется отдельно |

Если непонятно, что произошло, начните с `git status`. Прочитайте сообщение полностью: в нём часто указано, в какой области находятся изменения и что требуется для следующего шага.

<a id="section-14"></a>

## 14. Контроль версий при работе с ИИ

В первой лекции мы обсуждали ИИ-ассистентов и агентов. Их правки тоже нуждаются в истории и проверке.

Допустим, мы поручили ассистенту добавить доставку. Вместо одной формулы он изменил также вывод, названия переменных и описание. Сравнение версий помогает увидеть полный объём работы и проверить соответствие задаче.

Удобный порядок действий:

1. Начать с понятного состояния репозитория и сохранить завершённую работу.
2. Сформулировать конкретное изменение: «Добавь доставку один раз к общей стоимости».
3. После правок просмотреть `git status` и различия.
4. Проверить пример: `50 * 3 + 100` должно дать `250`.
5. Подготовить только относящиеся к задаче изменения.
6. Создать коммит с понятным сообщением.

Сообщение ассистента «готово» не заменяет проверку файлов. Коммит также не является доказательством правильности: он фиксирует выбранный результат и позволяет обсуждать его предметно.

<a id="section-15"></a>

## 15. Практическая работа: история программы покупки

### Часть А. Локальная история

Если вы уже выполнили разделы 8-10, продолжайте тот же проект и проверьте результаты; повторно создавать папку и дублировать коммиты не нужно.

1. Проверьте доступность Git и сведения об авторе.
2. Создайте `purchase-demo` с веткой `main`.
3. Сохраните программу без доставки и проверьте результат `150`.
4. Создайте коммит «Добавлен расчёт стоимости покупки».
5. Добавьте доставку 100 и проверьте результат `250`.
6. Перед фиксацией прочитайте обычный и подготовленный diff.
7. Создайте коммит «Добавлена стоимость доставки».
8. Добавьте README с описанием запуска и сохраните отдельным коммитом.
9. Добавьте `.gitignore` из раздела 10 и сохраните отдельным коммитом.
10. Выполните `git log --oneline` и объясните порядок записей.

**Ожидаемый результат:** четыре осмысленных коммита, программа выводит `250`, рабочая папка чистая. Число коммитов относится к этой последовательности, без дополнительных упражнений.

### Часть Б. Эксперимент с индексом

1. В существующем `purchase.py` измените количество с 3 на 4 и сохраните файл.
2. Выполните `git add purchase.py`.
3. Измените количество с 4 на 5 и снова сохраните файл.
4. Посмотрите `git diff --staged`: в нём должно быть изменение с 3 на 4.
5. Посмотрите `git diff`: в нём должно быть изменение с 4 на 5.
6. Объясните, почему сейчас обычный коммит сохранил бы количество 4.
7. Снова выполните `git add purchase.py`, проверьте подготовленные изменения и запустите программу.
8. Убедитесь, что результат равен `350`, затем создайте коммит «Изменено количество товаров на пять».

После повторного `git add` индекс содержит количество 5. Теперь подготовленный diff относительно предыдущего коммита показывает изменение с 3 на 5.

### Часть В. Графический клиент и сервер

1. Создайте на GitHub отдельный `purchase-desktop-demo` с README.
2. Клонируйте его через GitHub Desktop в отдельную папку.
3. Измените описание, просмотрите diff и создайте локальный коммит.
4. Отправьте коммит через Push origin.
5. Проверьте изменение в браузере.

**Что показать преподавателю:** историю локального проекта, результат программы, объяснение эксперимента с индексом и, если выполнена часть В, изменение на странице удалённого репозитория. Учётные данные и токены в отчёт не включаются.

## 16. Краткий словарь

| Термин | Значение |
|---|---|
| VCS | Система контроля версий |
| DVCS | Распределённая система контроля версий |
| Repository | Репозиторий: история и служебные данные проекта |
| Working tree / working copy | Рабочие файлы проекта |
| Index / staging area | Индекс, область подготовки следующего коммита |
| Commit | Фиксация выбранного состояния проекта |
| Commit message | Сообщение о назначении изменения |
| Diff | Представление различий между состояниями |
| Branch | Ветка, именованная линия разработки |
| HEAD | Указатель на текущее положение в истории; обычно связан с текущей веткой |
| Remote | Настроенный источник или получатель обмена с другим репозиторием |
| Origin | Обычное имя удалённого источника после клонирования |
| Clone | Создание локального репозитория из существующего |
| Fetch | Получение удалённых данных без их слияния с текущей веткой |
| Pull | Получение данных и интеграция в текущую ветку |
| Push | Отправка коммитов и обновление ссылок в другом репозитории |
| Merge | Слияние линий разработки |
| Conflict | Ситуация, требующая выбора способа объединения изменений |
| Fast-forward | Продвижение ветки вперёд по существующей истории |
| Untracked | Новый файл, ещё не включённый в отслеживание |
| Staged | Подготовленное к коммиту изменение |
| `.gitignore` | Правила игнорирования неотслеживаемых файлов |
